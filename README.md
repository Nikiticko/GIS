# GIS Calendar

Вебзастосунок для керування виробничими об’єктами. Вимоги описано в `PROJECT_SPEC.md`, карту проєкту — в `PROJECT_MAP.md`.

## Локальний запуск

Потрібні Node.js, npm і PostgreSQL. Налаштуйте `DATABASE_URL` у середовищі, потім виконайте:

```sh
npm ci
npm run db:migrate
npm run api:bootstrap-admin -- "Ім’я адміністратора" --show-code
npm run dev
```

Адміністратора створюють лише в порожній базі; код показується тільки в інтерактивному терміналі. Не зберігайте його в журналах.

## Підготовка до розгортання

`npm run build` збирає вебінтерфейс у `dist`, `npm run api:build` — сервер у `dist-api`. Для сервера доступні `npm run db:migrate:production`, `npm run api:bootstrap-admin:production` і `npm run api:start`. Вони запускаються з кореня проєкту. Перевірка доступності API та PostgreSQL: `GET /api/health`.

Вкладення зберігаються локально в каталозі `ATTACHMENTS_DIR` (типово `.local/attachments`). Обмеження активних вкладень одного об’єкта — 500 МіБ. Каталог і PostgreSQL необхідно резервувати разом.

HTTPS, запуск на VPS, автоматичне резервування на Google Drive і відновлення ще потребують налаштування та перевірки. Не використовуйте історичні демосхеми Supabase для робочої бази.

### VPS

Наведена конфігурація розрахована на Ubuntu з Docker Compose і каталогом проєкту `/opt/gis-calendar`. Спрямуйте домен на VPS і відкрийте порти 80 та 443. Скопіюйте `deploy/production.env.example` у `.env` на сервері, задайте домен та однаковий випадковий пароль PostgreSQL в обох параметрах; спеціальні символи пароля в URL потрібно закодувати. Не публікуйте цей файл.

Після першого автоматичного розгортання створіть адміністратора в інтерактивному терміналі VPS:

```sh
cd /opt/gis-calendar
docker compose -p gis-calendar --project-directory /opt/gis-calendar --env-file /opt/gis-calendar/.env -f current/compose.yaml run --rm api node dist-api/bootstrap-admin.js "Ім’я адміністратора" --show-code
```

### CI/CD

GitHub Actions перевіряє збірки, наявні тести й збірку контейнерів. Після успішної перевірки коміту в `main` він передає саме цей коміт на VPS, збирає контейнери, застосовує міграції та очікує готовності сервісів. Для pull request виконується тільки перевірка. Старі версії залишаються в `/opt/gis-calendar/releases`, а `current` вказує на останню успішну версію; томи БД і вкладень спільні. Автоматичного відкату міграцій немає: при помилці потрібна ручна перевірка та, за потреби, відновлення з резервної копії.

На VPS потрібні Docker Compose, `flock`, доступ користувача SSH до Docker і право запису в `/opt/gis-calendar`. Створіть каталог і `.env` до першого запуску. Для резервування використовуйте того самого користувача: у `deploy/gis-backup.service` за потреби замініть `User=gis-deploy` на ім’я користувача SSH. Це забезпечує спільне блокування резервування та розгортання. У GitHub створіть environment `production` та додайте до нього secrets `VPS_HOST`, `VPS_USER`, `VPS_SSH_PRIVATE_KEY`, `VPS_SSH_KNOWN_HOSTS` і, якщо порт не 22, `VPS_PORT`. Ключ SSH має дозволяти вхід на сервер; `VPS_SSH_KNOWN_HOSTS` містить перевірений ключ сервера у форматі known_hosts. Звірте відбиток ключа через панель провайдера або інший довірений канал. Не додавайте ці значення до репозиторію.

Перший запуск відбудеться після push у `main` із цією конфігурацією. Перевірте результат у вкладці Actions, потім створіть адміністратора та перевірте HTTPS і роботу застосунку. Доступ користувача до Docker надає широкі права на VPS, тому використовуйте окремий ключ для розгортання.

Caddy отримує HTTPS-сертифікат для домену. PostgreSQL та API не відкриваються назовні. Журнали контейнерів обмежені трьома файлами по 10 МБ; перегляд: `docker compose logs`. Міграція, що вимагає адресу, не застосовується до старих записів із порожньою адресою без попереднього виправлення даних.

### Резервні копії

На VPS встановіть rclone та налаштуйте Google Drive, а поверх нього — **crypt remote** `gis-encrypted`. Скрипт перевіряє, що обране сховище має тип crypt; прямий remote Google Drive не приймається. Збережіть ключі шифрування окремо від VPS; без них відновлення неможливе. Налаштування rclone має бути доступне користувачу, від якого працює systemd-сервіс.

Скопіюйте `deploy/gis-backup.service` і `deploy/gis-backup.timer` до `/etc/systemd/system/`, перевірте шлях і назву remote, виконайте `systemctl daemon-reload` та `systemctl enable --now gis-backup.timer`. Таймер запускається о 03:00 за Києвом. Журнал: `journalctl -u gis-backup.service`. У ньому також записується вільне місце. Скрипт тимчасово зупиняє API, створює узгоджену копію БД і файлів, перевіряє завантажену копію та видаляє копії старші 30 днів. Тимчасові незашифровані файли створюються на диску VPS і видаляються після завершення; потрібне достатнє вільне місце.

Резервування та відновлення обов’язково перевірте на окремій порожній базі й окремому каталозі до роботи з важливими даними. Налаштування Google Drive, перевірка відновлення та фактичний запуск таймера ще не виконані.

### Захист і оновлення

Перед запуском нової версії застосуйте міграції. Міграція `0005` переносить наявні токени сесій у SHA-256 без зміни cookie користувачів і додає таблицю обмеження спроб входу. Сервер перевіряє строк дії сесії (365 днів); ліміт входу зберігається після перезапуску API. Відкат на старий код авторизації після цієї міграції несумісний із хешованими сесіями.

Перед міграціями існуючої бази розгортання вимагає успішної копії БД і вкладень. На VPS попередньо налаштуйте rclone та remote `gis-encrypted:backups` для користувача SSH. Без налаштованого `crypt` розгортання зупиниться до міграції. Скрипт перевіряє тип remote, примусово вмикає шифрування даних, читає завантажену копію для звірки SHA-256 і перевіряє готовність API після його повторного запуску.

Завантаження обмежене двома одночасними запитами на API і одним на об’єкт. Квота перевіряється під час читання файла; під завантаження резервується місце з додатковим запасом 256 МіБ. Незавершені файли записуються в `.pending`, залишки старші доби очищуються. Максимальна тривалість завантаження — 15 хвилин. Типи файлів і загальний ліміт 500 МіБ на об’єкт збережено.

Ізольовано перевірено міграцію заповненої тестової бази, авторизацію, квоту файлів і відновлення PostgreSQL та вкладень. Це не замінює перевірку справжньої копії Google Drive на VPS. Окремо залишаються налаштування обмеженого користувача PostgreSQL замість адміністративного та шифрування персональних ключ-кодів: останнє потребує окремого ключа, який має зберігатися поза базою. Персональні ключ-коди поки зберігаються в базі у вихідному вигляді.
